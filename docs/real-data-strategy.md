# Real-data strategy: 300,000 real Pakistani businesses with WhatsApp

**Status:** research + Phase 0 shipped · prepared 2026-11-04
**Question asked:** ship 300k listings of *real* Pakistani entities (corporates and other
sectors), each with a working WhatsApp button on a *real* number.

---

## 1. First: correcting the "28 contacts" figure

Two different numbers were being conflated.

| Number | Meaning |
|---|---|
| **62,283** | Distinct mobile numbers the directory can open a WhatsApp chat with today. That is **31% of the 200,000 rows**. |
| **28** | New *automated assertions* I added to the test suite in the last change. Unrelated to listing counts — I should have been clearer about that. |

Measured on the shipped dataset (`public/data/directory.txt`):

```

landline numbers          51,258   25.6%   <- button degrades to "Copy number"
"confirmed on WhatsApp"   62,292   31.1%
distinct chat-capable nrs 62,283
```

So coverage was never 28. The real problem is different, and bigger — see §2.

## 2. The uncomfortable finding: those 200k records are not real businesses

They are **deterministically generated filler**. `scripts/generate-data.mjs` invents names
from word banks (`Al-Madina`, `Star`, `Royal` × `Biryani`, `Motors`, `Textiles`) and
`src/lib/derive.js` derives the phone number:

```js
const isMobile = rand() < (city.mobileBias ?? 0.55);
phone = `${pick(rand, prefixes)}-${randInt(rand, 1000000, 9999999)}`;  // e.g. 0307-4821193
const whatsapp = isMobile && rand() < 0.42;                            // coin flip
```

Consequences that matter for the product:

- **The numbers are random.** A `0307-4821193` in a Karachi card may well belong to a real
  person in Chiniot. Publishing 148,742 of those as "WhatsApp this business" means sending
  strangers to strangers.
- **Duplicate entities are generated by design.** Banks, franchises, courier offices and
  hospitals each have 30–2,000 branches in reality; the generator produces one row with no
  branch concept.
- **City distribution is zipf-ish but not real.** Karachi 9.5%, Lahore 7.0% — real Karachi
  business density is far higher relative to its population weight.
- **The README and several pages called them "verified".** That was wrong and is now
  corrected (§6).

This is fine for a demo — it is not fine for a lead CSV that an agency pitches from.

## 3. What the data landscape actually looks like

### 3.1 Volume is not the bottleneck. Contact data is.

| Source | Rows | Phone numbers? | WhatsApp? | Licence | Verdict |
|---|---|---|---|---|---|
| **SECP corporate register** | **258,000+** companies (FY25, record 35,000 registrations in one year) | ❌ typically just registered address | ❌ | Public register, no bulk export API; paid extracts | The real *corporate* spine. 258k ≈ your 300k target on its own. |
| **FBR Active Taxpayer List (ATL)** | Large multi-hundred-thousand list, downloadable **xlsx** | ❌ names + NTN/CNIC only | ❌ | Public list, captcha-gated download | Excellent **verification** layer and coverage check; useless as a phone source. |
| **PSX listed companies** | ~550 | ✅ via company sites | ❌ | Public | Tiny, but the highest-value corporate slice — worth hand-curating. |
| **Overture Maps places** (Meta/Microsoft/Foursquare/AllThePlaces…) | 81M worldwide; Pakistan slice not yet measured | ✅ `phones` array | ❌ | **CDLA Permissive 2.0 / Apache 2.0** — commercial use OK, attribution required | Best free bulk POI + phone source. |
| **OpenStreetMap (Geofabrik PK extract)** | — | **only 9,679 objects in all of Pakistan have `phone`** | **1 object in Pakistan has `whatsapp`** | ODbL (share-alike) | Too thin to carry a directory; good for addresses/map pins. |
| **opendata.com.pk (CKAN)** | 1,471 datasets; "Yellow Pages of Pakistan" = **67,000** businesses | ✅ telephone column | ❌ | PDDL — but **sourced from findpk.com**, a 2021 scrape | Legally murky, stale, must be re-verified per record. |
| **Commercial vendors** (Yellow Pages PK, businesslist.pk, data resellers) | 100k–1M | ✅ | partial | Paid, per-seat/redistribution terms | Fastest path to real volume **if you can pay and the licence permits resale**. |
| **Own number** — owner submissions + WhatsApp Business Profile | grows from 0 | ✅ | ✅ | Yours | The only source that can be *verified* and kept fresh. |

### 3.2 258k (SECP) + phone numbers do not come from the same place

There is no public source that gives you *company name + real phone + WhatsApp status*
for 300,000 Pakistani entities. Any claim otherwise is selling you a scraped list. To hit
300k you have to **join** sources: registry/company identity from SECP/PSX/vendor, and
contactability from Overture/vendor/owner submissions.

### 3.3 "Must have a WhatsApp button with real numbers" — what is technically possible

**Meta removed the ability to check a number's WhatsApp presence.** Per the Cloud API docs
(July 2025 pricing change):

> "With the Cloud API, there is no longer a way to explicitly check if a phone number has
> a WhatsApp ID."

So the idea of *bulk-verifying* 300k numbers as WhatsApp is not possible through official
channels at any price. What **is** possible:

- **Click-to-chat is free and needs no verification** — `https://wa.me/92…` works for any
  number that has WhatsApp. If it does not have WhatsApp, WhatsApp shows "phone number
  shared via link is invalid". That is why the app now only renders a chat button for
  `03xx` mobiles and offers *Copy number* for landlines.
- **Verified coverage** can only come from **owner opt-in**: the owner taps "message us on
  WhatsApp" from the app (which proves the number is live, because *they* initiated), or
  you connect the WhatsApp Business Platform and use **service messages** (free, inside the
  24-hour window) to confirm a number when it replies.
- **Bulk outbound verification is the expensive path**: Cloud API intake is per delivered
  template message, and cold outreach without opt-in breaks Meta's Business Messaging
  Policy and risks the number being banned. Treat it as verification-by-reply at low
  volume (thousands, not hundreds of thousands).

**Conclusion:** 300k listings with a WhatsApp *button* is achievable. 300k listings with a
*verified* WhatsApp number is not, by anyone, without ~300k owners opting in. The honest
product target is a **coverage gradient**, which the app now displays and exports:

```
Owner verified      <- number confirmed via owner opt-in (or a reply). Highest trust.
Official registry   <- entity confirmed in SECP/PSX/ATL; phone may be the registered line.
Dataset             <- real place + phone from a licensed dataset, not re-confirmed.
Sample              <- generated demo filler. Never presented as real, never dialled.
```

## 4. Legal and policy considerations (read before importing)

1. **`wa.me` cold outreach is legal-risky at volume.** Pakistan's **PECA 2016 s.25**
   covers unauthorised access; more relevant is Meta's Business Messaging Policy: unsolicited
   bulk messaging gets numbers banned. The app's one-tap-per-lead queue is deliberately
   manual — keep it that way; do not add automated blasting.
2. **Database right / licence chains.** `opendata.com.pk`'s Yellow Pages set is derived from
   findpk.com with a PDDL stamp. Republishing a scrape of a commercial directory can breach
   the original site's terms even if the repackager says PDDL. Prefer Overture (explicitly
   CDLA-2.0, commercial use permitted) or a paid vendor with resale rights in writing.
3. **ODbL share-alike.** Mixing OSM data into a directory can make the whole derived
   database ODbL. Overture is deliberately non-OSM for this reason.
4. **Personal data.** Many SME numbers are personal mobiles. Keep an audit trail
   (`source`, `sourceRef`, `capturedAt`), honour removal/takedown requests fast, and never
   export a number you cannot point at a source for.
5. **Attribution.** Overture requires attribution in the UI/About page; OSM requires
   "© OpenStreetMap contributors".

## 5. The path to 300k real listings

**Phase 0 — stop the trust leak (shipped with this PR)**
Provenance model, honest labels, sample rows that cannot be dialled, provenance columns in
CSV, and a real import pipeline (`scripts/import-listings.mjs`).

**Phase 1 — free real spine (~1 week)**
1. Overture places for Pakistan (nationwide bbox), keep records with a phone.
2. Hand-curate corporates: ~550 PSX listed + top 200 groups + banks/telecoms/universities
   (the existing `src/data/curated.js` pattern already does 91).
3. FBR ATL as a *verification* join: mark entities that appear in ATL as `Official registry`.

**Phase 2 — volume (~2–4 weeks, commercial decision)**
4. Buy a licensed Pakistani business dataset with phone numbers (or negotiate a
   redistribution licence). This is the only realistic route through 300k.
5. If no budget: Overture + owner submissions + public sector/association member lists
   (chambers of commerce, PIAF, APTMA, FPCCI member directories) — expect 60–150k depending
   on how many associations publish machine-readable lists.

**Phase 3 — verified WhatsApp (ongoing, ~2 months to first 10k)**
6. Claim-your-listing flow → owner confirms number → `source: owner`.
7. WhatsApp Business Profile link on each listing: owner taps "message us" → number proven
   live → flag `whatsappConfirmed`.
8. Measure the gradient: target 10k owner-verified numbers in 90 days, not 300k.

## 6. What changed in this PR

- `src/lib/provenance.js` — one source of truth for trust (`owner` / `official` / `seed` /
  `dataset` / `sample`).
- Generated rows now declare `source: 'sample'`; curated rows declare `source: 'seed'`.
- **Sample rows never get a WhatsApp chat button or a verified badge**: the button becomes a
  disabled "Sample" control that says why. Profile pages carry a warning strip.
- Cards show `🧪 SAMPLE — NOT A REAL BUSINESS`.
- `leadsToCsv` adds **Source** and **Trust** columns so an agency can filter filler out.
- `scripts/import-listings.mjs` — Overture (`--source=overture --bbox=…`) and CSV/registry
  (`--source=csv --in=… --as=official`) importers; drops rows with no phone, de-dupes,
  downgrades WhatsApp claims on landlines, keeps `sourceRef`/attribution.
- Removed unsupported "verified" claims from Home, Browse, Nearby, Business Detail, FAQ copy.
- 18 new tests: `99 passed, 0 failed`.
